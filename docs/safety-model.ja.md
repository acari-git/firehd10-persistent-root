# 安全モデル

> English: [safety-model.md](safety-model.md)

設計原則は **フェイルクローズ、そして端末を素の状態より悪くしない
こと**。すべてのコンポーネントはこの原則の下で構築され、受入テストを
受けた。

## 決して書き込まないもの、決して試みないもの

- boot / recovery / LK / preloader / system / vendor パーティションへの
  書き込みは一切なし。フラッシュなし、OTA の操作なし、ダウングレード
  なし。
- ブートローダーはロックされたまま、Verified Boot は green のまま。
  root は **ブートごと、メモリ内** のチェーンであり（tmpfs の Magisk)、
  ROM は決して改変されない。したがって、システムを武装解除した素の
  再起動で、端末は完全に素の振る舞いに戻る。
- より古く、より悪用しやすいファームウェアへのダウングレード経路は
  当初に評価され、却下された：この端末では、低レイヤーの復旧手段の
  ない、回復不能な RPMB ブリックのリスクがあるためである。

## フェイルクローズの意味論

- **ジャーナルによる拒否。** 欠落、外部形式、古い、あるいは矛盾する
  ジャーナル／witness／チャレンジの状態は、試行を拒否する。v1 形式の
  ジャーナルレコードは、設計上 v2 ジャーナルにとって *外部のもの* で
  あり、解釈もクリアもされない。
- **ワンショットの武装。** 武装は試行によって消費される。再武装は、
  検証された証明の完了を通じてのみ成功する。**いかなる** 失敗 —
  キャリアのミス、タイムアウト、拒否 — も persist フラグを 0 に残す。
  ブートを跨いで静かにリトライするものは何もない。
- **署名者のゲート。** 署名者は呼び出しのたびに自己検証を行い（実行
  コンテキスト、鍵の保管、Enforcing 状態）、ゲートが失敗すれば署名を
  拒否する。使用済みチャレンジの台帳は署名前にチャレンジを消費する
  ため、リトライが生みうるのは `challenge_reused` の拒否だけである。
  したがって呼び出し側は決して拒否をリトライしない。署名の試行は
  ブートごとに正確に1回。
- **ヘルパーの姿勢チェック。** 起動ヘルパーはすべての停止条件を自ら
  再検証し（persist フラグ、両方の sentinel、起動ラッチ、スロットの
  状態）、他のアクターの武装を横取りすることを拒否する。完了ワーカーは
  ジャーナル、いかなる Settings 値、persist フラグ、どちらの sentinel
  にも決して書かない — 書くのは自らのログと tmpfs のロックだけである。
- **Sentinel。** 2つの独立した disable ファイル
  （`/data/cache/snusnu/disable` と、保護されたストレージにおける
  同等物）が、それぞれシステム全体を止める。コンポーネントは両方を
  尊重する。

## root の窓と SELinux

一時 root は Stage4 の窓の内側にのみ存在する。成功したすべてのブートの
落ち着いた状態は **MagiskSU が生きている SELinux Enforcing**
（`u:r:magisk:s0`）である。落ち着いた状態で読み込まれるポリシーは
667,117 バイトであり、素の 651,815 バイトに対する差分は Magisk の
ルールセットで、プロジェクトの受入ゲートの一環として監査された。
（正直に開示する：Magisk ドメインの権限は設計上広い — それは Magisk
自体の性質であり、ゲート監査でレビューされ受け入れられたもので、
隠されてはいない。）

カーネルパニック、あるいは予期せぬ Recovery への遷移は、いかなる運用
セッションも即座に終了させる。常設の指示は、即興で対処せず、端末を
Recovery のままにしておくことである。

## セッション規律（どのように運用されたか）

- リトライは既知で安全な `ENODATA` ミスのクラスに対してのみ、1シーケンス
  あたり最大3回まで。成功の判定は、実際の SELinux 状態と本物の
  `uid=0` チェックによって行い、スクリプトの終了テキストだけでは
  決して行わない。
- 状態を変えるすべてのステップは、ツールが報告する状態にかかわらず、
  独立した読み戻しで検証される。
- コンポーネントはハッシュピン留めでインストールされる：インストーラは
  前後で SHA-256 を検証し、所有者／モード／ラベルを明示的に設定し、
  不一致があればフェイルクローズする。

## 正直な限界

- Stage4 キャリアは **確率的** である（`failure-modes.ja.md` を参照）。
  ミスしたブートは安全だが武装解除されており、戻すには root セッション
  上での文書化された復旧フローが必要であり、それ自体がホスト駆動の
  再取得の成功を必要とする。
- 本システムは正確に1つのファームウェアビルドで検証されている。ここに
  書かれたことは、他のビルドで試しても安全であることを示唆するものと
  読んではならない：ドライバの事前チェックはそれらを拒否し、その拒否は
  安全モデルの一部である。
