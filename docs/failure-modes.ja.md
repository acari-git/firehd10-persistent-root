# 失敗モード

> English: [failure-modes.md](failure-modes.md)

以下のすべては実機で観測されたものであり、システムがこの形をしている
理由の一部である。

## ENODATA：確率的なキャリアのミス

Stage4 のリーク段階は、スプレーされたカーネルオブジェクトを読み戻す。
ミスは `LIST_POISON2` の署名（`node=0xdead000000000200`）を示す —
RCU のグレースピリオド／kmalloc 再利用のレースであり、スプレーされた
スロットが間に合うように再利用されなかった。歴史的に最も多いミスの
型であり（記録されたミス10件のうち7件）、**ブートごとの抽選** で
あって、劣化していく状態ではない：

- 2026年10–11月のドライバ Phase B の記録：**9/19 ≈ 47%**。この
  割合では、3回連続のミス（確率 ≈0.21）は特筆すべきことではなく —
  実際、歴史上最長の連続ミス（2026-10-11、そして再び 2026-11-02）も
  3回であり、いずれも後の新規ブートで解消した。
- ログの比較では、識別できる変数は見つからなかった：saved_time の
  差分、ブートカウントの偶奇、時刻は、成功とミスの間で完全に重なる。
  異なる出力はリーク段階そのものだけである。
- ミスは **カーネル書き込みを行わない**
  （`ENODATA_LEAK_MISS_NO_WRITE`）。端末は素の状態に戻り、新規ブートで
  リトライできる。

そこから導かれる運用ルール：リトライはこのミスのクラスに対してのみ、
1シーケンスあたり最大3回まで。キャリアのパラメータを「確率を上げる」
ために決して変えない（ハッシュピン留めされた 10 ms ビルドはそのまま
保持する）。

## ミスした武装ブートは武装解除する（設計どおり）

ブート209（2026-11-02、12.5時間の電源断の後の最初の電源投入）：
アプリ側キャリアが試行1でミス → `enodata_exhausted`、
`proof_status=proof_rejected`、そしてアプリは武装を消費し、再武装
**しなかった**（persist 1→0)。ジャーナルは INFLIGHT のままだった。
これはフェイルクローズの契約が設計どおり働いた姿である — しかし
同時に、ミスしたブートは自己修復しないことを意味する：復旧には
`genesis.ja.md` のホスト駆動フローが必要である（root 再取得 →
sign-genesis ロックアウト復旧 → 再配置 → 再武装）。アプリ側の武装
ブートは 9/10 と測定されており、したがってこれは異常ではなく、
安全性の姿勢に伴う、時折の、想定されたコストである。

## 測定によって見つかった欠陥と、その修正

- **チャネル応答のデッドロック。** システムチャネルのゲートは、決して
  終了しない対話的シェルで終わる。アプリは当初ハーフクローズを決して
  行わなかったため、コマンドの応答は 120 秒のタイムアウトへデッドロック
  した（ブート195：起動は実際には端末上で成功していたが、アプリは
  タイムアウトして武装解除した）。修正：アプリは送信後に flush し
  `shutdownOutput()` する。ゲートのシェルは EOF を見て、応答が戻る。
  プロジェクト全体に記録された教訓：状態を変えるすべてのコマンドを
  独立した読み戻しで検証せよ — このプロジェクトで「拒否された」リフトの
  1つは、実際には、状態不明の結果の下で実行されていた。
- **ヘルパーの結果書き込みに対する AVC 拒否。** 起動ヘルパーの
  tmp＋rename による結果書き込みが拒否され（rename、system_app→
  cache_file)、レコードが失われた。修正：直接書き込み。
- **古い genesis ドロップの再評価。** アプリは処理済みのドロップを
  決して削除しない。消費済みの genesis ドロップが、後に新しいチャレンジ
  に対するロックアウト復旧の候補として再スコアされ、`proof_status` を
  `genesis_rejected` へ反転させた。ジャーナルや保管への損傷はなし
  （失敗した試行は何も書かない）。修正は、genesis ブランチをチャレンジの
  一致でゲートし、消費済みのドロップを不活性にする。
- **完了ワーカーのコンテキスト読み取り。** ファームウェアの `tr` は
  `\0` エスケープを壊し、`u:r:magisk:s0` の `r` を食い、それはワーカーに
  自らのコンテキストを拒否させるところだった。修正：`tr` の代わりに
  コマンド置換による正規化。
- **古いドロップによる再開。** 素朴な「ドロップが存在する → 署名を
  スキップ」再開チェックは、次のブートでの署名を抑制してしまうところ
  だった（前ブートのドロップがまだディレクトリに残っている）。ワーカーは、
  ドロップの署名付きメッセージが *この* ブートと保留中のチャレンジに
  結び付くことを要求する（`drop_fresh`)。古いドロップは `DROP_STALE`
  として記録され、上から署名される。

## 設計を形作ったプラットフォームの癖

- **TimeService がブートを跨ぐ武装を食う。** `persist.sys.saved_time`
  は NTP 同期によって数値で上書きされる（ブートの約20秒と約130秒、
  さらにゲートのない日次タイマー）。したがって *後の* ブートのために
  武装されたトリガーは蒸発する。10月のポーリング再武装ウォッチドッグは
  これに対抗したが、それはまさに禁じられた早期再武装のパターンである。
  採用された答えは、ブート内、ジャーナルでゲートされたオンデマンド
  起動である。
- **USB 給電での自動ブートなし**（実測）：冷起動のテストには、電源
  ボタンに人間の手が必要である。
- **`su -c "reboot -p"` が、ある測定されたブートで電源断ではなく
  再起動した**。信頼できる電源断の経路は、root でない
  `adb shell reboot -p` である。
- **アプリは素の Enforcing の下ではカーネルのブート id を読めない**
  （アプリドメインからの proc_random 拒否）：したがって無人のジャーナル
  begin は劣化した同一性の形を使い、waiter の witness が完了時点の
  主張を担う。

## ログでは決定できないこと

ブートごとの RCU／再利用のマイクロタイミングはカーネル側の記録を残さず、
アプリのチェーンは HWBINDER の値を記録しないため、ドライバとアプリの
成功の差（7/17 期のドライバ記録 対 9/10 のアプリサイクル）を、ログだけ
からチェーン対タイミングの効果へ完全に分解することはできない。今後の
計装の提案（未実装）：アプリ側の Settings マーカーに `HWBINDER_STATEFUL`
の結果を記録すること。
