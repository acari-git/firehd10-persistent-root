# firehd10-persistent-root

**Amazon Fire HD 10（trona）/ Fire OS 7.3.3.1 向けの、完全無人で
永続化する root システム — SnuSnuRoot の上に構築した、ジャーナル
管理・フェイルクローズな永続化レイヤー。**

> English version: [README.md](README.md)

## これは何か

voidnullvalue 氏の [SnuSnuRoot](https://github.com/voidnullvalue/SnuSnuRoot)
は、このタブレットに *一時的な* root を提供します：確率的な
カーネルレースに勝ち、root の窓を得て、再起動で失う。本リポジトリは、
その上に構築したレイヤーであり、root を **永続化し、完全無人化**
します：

- 武装されたブートは毎回、自動で root を再取得し、Magisk を配置し、
  MagiskSU を生かしたまま SELinux Enforcing を復帰させ、端末内
  ECDSA 署名でサイクルを証明し、次のブートを再武装します —
  約90秒、操作者もホストもケーブルも不要です。
- 武装は二相の **ジャーナル** が管理します：ブートが試行できるのは
  READY レコードからのみで、試行を完了し次を武装できるのは検証
  された署名付き証明だけです。失敗はいずれも、システムを中途半端に
  武装したままにせず、武装解除します（フェイルクローズ）。
- 正式な受入シーケンスでエンドツーエンド検証済み： **5/5**
  （通常再起動3回＋電源を切った状態からの冷起動2回、すべて無人）。
  途中での失敗、完全な復旧、再テストを経ての結果です。

## これは何でないか

- **新しいエクスプロイトではありません。** 一時 root のチェーンは
  上流のものです。本リポジトリに Stage4 ペイロードのバイナリは
  含まれません（参照のみ。`UPSTREAM.md` を参照）。
- **ブートローダーアンロックではありません。** trona には知られた
  正規のアンロックが存在せず、本システムは意図的にそれなしで
  動作します：ブートローダーはロックされたまま、Verified Boot は
  green のままです。
- **ROM の改変ではありません。** 設計上、boot / recovery / LK /
  preloader / system / vendor には一切書き込みません。root は
  ブートごとのメモリ内チェーンです。武装解除して再起動すれば、
  端末は素の状態に戻ります。

## アーキテクチャ（概要）

- **ジャーナルによる武装管理** — `Stage4AttemptJournalV2`：EMPTY /
  INFLIGHT / READY。ジャーナルが *唯一の* 武装権限です。歴史的な
  ポーリング再武装ウォッチドッグのパターンは明示的に採用して
  いません。
- **端末内署名者＋証明による完了** — 端末内で生成された ECDSA
  P-256 鍵（秘密の半分は端末から決して出ません）が、INFLIGHT
  レコードと試行ごとのチャレンジに結び付けられた、ドメイン分離
  された証明に署名します。アプリは、ビルド時に APK へピン留め
  された公開鍵で検証します。
- **三層のブート同一性** — 署名者の `/proc` アンカー、waiter が
  書くブート witness、ブートカウントラッチ。
- **オンデマンドの waiter 起動** — 武装はジャーナルブートの内側で
  起きます（素の `ctl.start`）。TimeService がブートを跨ぐ武装を
  数秒で破壊するためです。
- **署名者の自動完了** — Magisk ドメインのワーカーが Enforcing
  復帰マーカーに同期し、署名者に保留中の証明リクエストへ署名させ
  （試行1回）、アプリを再トリガーします。
- **証明による再武装の閉包** — persist フラグを再武装するのは、
  検証された通常完了のみです。genesis とロックアウト復旧による
  完了は武装しません。

## 実測の信頼性（開発端末、2026年10–11月）

| 経路 | 割合 |
|---|---|
| ホスト駆動の再取得、新規ブートごと | 9/19 ≈ 47% |
| アプリ側の無人サイクル、武装ブートごと | 9/10 |
| 正式受入シーケンス | **5/5**（通常再起動×3＋冷起動×2） |

Stage4 リーク段階でのミス（`ENODATA`）はカーネル書き込みを行わず、
端末を素の状態に戻します — しかし *武装された* ブートでのミスは
システムを武装解除し、再武装には文書化された復旧フロー（root
セッション＋sign-genesis ロックアウト復旧）が必要です。この
トレードオフ — 自己修復より安全 — は意図的なものです。

## ビルド方法

Gradle は使いません。ビルドは POSIX `sh` と、Android SDK
コマンドラインツールのインストール、および JDK 17 です：

1. 上流をピン留めされたコミットで取得します。`app/build.sh` は
   署名キーストアを `<app>/../../refs/SnuSnuRoot/poc/snusnu-persist-app/signing/snusnu-debug.keystore`
   として解決します — 本リポジトリのレイアウトでは、それは
   リポジトリの *親* ディレクトリにある `refs/` ディレクトリです。
   上流のチェックアウトを `refs/SnuSnuRoot` として、そこへ配置
   またはシンボリックリンクしてください（開発ツリーでは、同じ
   `refs/` はビルドのルート、app の2つ上にありました）。
2. `app/build.sh` が通常のビルドを実行します（javac `-source 8 -target 8`
   → jar → `d8 --min-api 28` → `aapt2 link` → `apksigner` v1+v2）、
   チェックインされたピン留め鍵を使って。先に自分の公開鍵を
   ピン留めするには、`python3 app/gen_pinned_key.py <your-public.der> "<label>"
   app/src/io/github/voidnullvalue/snusnuroot/persistence/Stage4PinnedProofKey.java`
   を実行してから `app/build.sh` を実行します（`docs/genesis.ja.md`
   を参照）。`app/build-v2.sh` はこの2ステップを連鎖させる
   開発ツリー用ラッパーで、開発レイアウト（隣接する
   `stage4-persistent/` ディレクトリ）を前提としており、来歴の
   ために残されています。
3. SDK の検出： `SNUSNU_SDK`、次に `ANDROID_SDK_ROOT` /
   `ANDROID_HOME`。

**署名についての開示。** 参照ビルドは上流の **公開デバッグ
キーストア** で署名します。再ビルドした APK が `pm install -r` で
アップグレード互換を保つためです。したがって、この署名には
**発行者の真正性は一切ありません** — 誰でも作ることができます。
本システムの信頼の錨は、ビルド時にピン留めされる端末ごとの
ECDSA 証明鍵であり、APK の証明書ではありません。ビルドするなら、
自分が読んだソースからビルドしてください。

**リリース APK は提供されません**（v1 はソースのみ）。理由は
まさに上記のとおりです。
